==============================================================================
B1(a)  KV-cache bytes per token
==============================================================================
One cached token needs a K vector and a V vector in every layer.
With grouped-query attention the cache is sized by the KV head count (8),
not the query head count (24) -- that is the whole point of GQA.

  bytes/token = 2 (K and V)
              x layers        (28)
              x kv_heads      (8)     <- GQA: 8, not 24
              x head_dim      (128)
              x bytes/elem    (2)     <- fp16 KV cache

  = 2 x 28 x 8 x 128 x 2
  = 114,688 bytes/token  =  112 KiB/token

  Sanity check -- if someone wrongly used the 24 query heads:
    2 x 28 x 24 x 128 x 2 = 344,064 bytes/token (3x too big)

  One full 4096-token sequence: 114,688 x 4096 = 469,762,048 bytes = 448.0 MiB = 0.470 GB

==============================================================================
B1(b)  How many concurrent 4096-token sequences fit
==============================================================================
  weights        = 4.2e+09 params x 2 B = 8.40 GB
  overhead       = 1.60 GB (given)

  The spec says '24 GB' and vLLM's gpu_memory_utilization applies to
  total device memory, so the GB-vs-GiB reading of '24' matters. Both:

  interpretation                    usable       KV pool  max tokens    max seqs

  ------------------------------------------------------------------------------
  24 GB  (decimal, 24e9)          22.08 GB      12.08 GB     105,329       25.72
  24 GiB (binary, 2^30)           23.71 GB      13.71 GB     119,526       29.18

  Arithmetic for the decimal reading, in full:
    24.00 GB x 0.92                 = 22.08 GB usable
    22.08 - 8.40 (weights) - 1.60 (overhead) = 12.08 GB for KV
    12.08 GB / 114,688 B per token       = 105,329 tokens
    105,329 tokens / 4096                = 25.7 sequences  -> floor 25

==============================================================================
B1(c)  Check the prediction against bench_log.csv

kv_cache_util is the fraction of the KV pool in use. Inverting it on
each row gives an OBSERVED pool size, in tokens and in 4096-tok seqs.
kv_cache_util is logged to 2 decimals, so rows below ~0.05 are dominated
by rounding (at util=0.01 one ulp is +-50%) and are excluded from the mean.
